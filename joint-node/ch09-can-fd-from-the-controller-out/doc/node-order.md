# The configuration order, as the node will walk it

Chapter 9 stage two, Thursday 8 October 2026. The values are in
[node-registers.md](node-registers.md); this is the sequence, and the sequence is
the half that cannot be debugged on the board.

Three of the four things that were guessed about this order on Wednesday
7 October 2026 were guessed wrong, and **all three fail silently**. An
uninitialised message RAM reads back as a parity error that presents as a bus
fault. A test register written before the control register is a write to a locked
register, so loopback stays off while every other bit reads back exactly as
intended. And a global filter of zero accepts rather than rejects, so the value
that looks like a cautious default is the one that makes receive work at all.

A sequence whose mistakes are invisible on the hardware does not belong in
hardware code. So it is not written as a function that configures a controller.
It is produced as **data** by `fdcan_plan` in `src/bus/initplan.c`, which touches
no register and names no vendor header, and `src/bsp/` will walk the list. That
also satisfies chapter 4's rule, which exists so chapter 20 can build this node
on a host.

## What this buys

The order is checked on a laptop with no controller on it, and checked twice over:

| Check | Catches |
|---|---|
| The plan matches the committed vectors | drift, and a hand edit of either side |
| The plan obeys seven ordering rules | a sequence that is **wrong**, which the vectors cannot see, because a vector file regenerated from a wrong generator agrees with it perfectly |

That second row was proved rather than asserted. Four mutations were applied to
the reference, the vector file was regenerated each time so that it agreed with
the mutation, and the test was watched going red on the invariant alone:

| Mutation | Reported by |
|---|---|
| the message RAM clear removed | "the message RAM is never cleared" |
| `TEST` written before `CCCR` | "TEST at step 18 is written before CCCR unlocks it" |
| `MON` dropped from internal loopback | the distinct-plans rule, which noticed internal and external had become the same thing. The `MON` rule would have fired too |
| `INIT` released before `CCE` closed | "CCE is never cleared, so configuration is left open" |

## Three steps that are not obvious from the table

**Step 1 and 2 write nothing.** `CREL` says which M_CAN core version this part
carries, which is the last open question that can change code. `ENDN` is checked
rather than merely read, because it has exactly one correct answer, `0x87654321`,
and a wrong base address reads back as zeroes that look like a peripheral which is
simply unconfigured. Proving the block answers before writing to it costs two
reads.

**Step 5 clears 2432 bytes and not 10240.** The part has 10240 bytes of message
RAM shared between its two FDCAN instances, and this layout uses 2432 of them.
Clearing only what is in use is what the driver does, and it is also the honest
bound: the rest belongs to an instance this volume does not configure.

**Step 15 writes a register for a section with no elements in it.** `RXBC` points
at the receive buffers, and this layout asks for none. It is written anyway,
because the reset value points somewhere, and somewhere is not nowhere.

## What is still not written

This is the plan, not the image. What remains is `src/bsp/`, which is where the
silicon may be named:

| Piece | Note |
|---|---|
| Startup and a linker script | vector table, reset handler, `.data` and `.bss` |
| HSE in bypass mode | the only FDCAN clock that needs no PLL, and `FDCANSEL` is already at its reset `00` |
| `PD0` and `PD1` to alternate function 9 | on `CN11`, the connector that prints port names |
| A console on USART3 | `PD8` and `PD9`, believed by convention and corroborated by an image printing through it on Wednesday 7 October 2026 |
| The executor | a loop over the plan, reading back every `modify` and reporting the step that failed by name |
| Transmit and receive | a transmit element written into the RAM, `TXBAR` to send, `RXF0S` and `RXF0A` to collect |

None of that can be built on the authoring laptop, and none of it is written yet.
The plan above is the part that could be checked without it, which is why it was
done first.
