# Message memory layout, and where an element lives in it

Both tables on this page are generated. Each one says by which tool, and
neither survives a hand edit.

## The layout

Generated by `python tools/gen_msgram.py --table`. Do not edit by hand.

A controller whose message memory has not been laid out accepts every other
configuration, reports no error, and never transmits. The layout is therefore
computed and asserted rather than written down, and the sections tile the space
with no hole and no overlap.

Element sizes differ by section: a standard filter is one word, an extended
filter and a transmit event are two, and a receive or transmit element carrying
the full sixty-four byte payload is eighteen.

## Where an element lives

Generated by `python tools/gen_msgaddr.py --table`. Do not edit by hand.

The table above gives each section's offset. Getting from there to one element
is a multiply and an add, and `src/bus/msgaddr.c` exists because the multiply
and the add return a plausible wrong answer in three ways.

**An empty section has a perfectly good offset.** Read the table above again:
`rx_buffers` is at offset 1792 and so is `tx_event`. This node configures no
dedicated receive buffers, so the two sections begin at the same place. Ask for
receive buffer 0 and the arithmetic hands back 1792 without complaint. Write
there and the first transmit event is overwritten. Read there and an event comes
back shaped like a frame. Nothing in the controller reports either, so the
symptom appears wherever the event FIFO is next read, which is somewhere else
entirely.

**The sections do not share an element size.** One word, two words or eighteen,
by section. Index times the wrong size is an address partway through a
neighbouring element, and a frame read from there is the tail of one frame
followed by the head of the next.

**An offset is not an address.** The start-address registers hold offsets from
the message memory base; a pointer needs the base added. For transmit buffer 0
those are `0x0740` and `0x4000B340`, and both look like reasonable numbers. The
register fields in [node-registers.md](node-registers.md) are where this chapter
got that wrong the first time, which is why the two are separate functions whose
names carry the word rather than one function and a comment.

### What the checks actually proved

Two mutations, each with the vectors regenerated to agree with it, so only the
rules could object.

Removing the empty-section refusal alone **did not** turn the checks red, and
that is worth stating rather than hiding: the span check caught it instead. The
two guards are the same arithmetic whenever the layout's count and the map's
byte span agree, which they do unless one of the two has drifted. The span check
earns its place only in that case, and the count check is the one doing the work
the rest of the time. With both guards removed the rules fail and name the
colliding section: `rx_buffers is empty and index 0 was given an offset, which
is tx_event`.

Addressing every section as though its elements were one word produced 84
failures, 39 of them naming the two elements that had come to share memory and
the rest from the contiguity, alignment and inside-its-own-section rules. The
counts are from the run's own output, not from an estimate.
