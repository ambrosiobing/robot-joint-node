# The device interrupt vector table

Recorded on Monday 9 November 2026. Until that day `startup.c` carried the
sixteen core exceptions and nothing else, with a `[unconfirmed]` note saying the
device positions had to be read from a source and had not been. This is that
source, read.

The table below is generated by `tools/gen_vectors.py --table`. Nothing here is
typed by hand, because it is 155 rows of numbers and the only mistakes available
in it are silent ones.

## Where the numbers come from

Two vendors, independently, and they agree.

`[vendor]` **The 155 positions and their names are ST's own**, from the
`IRQn_Type` enum in the CMSIS device header for this exact part,
`Include/stm32h7a3xx.h` in `STMicroelectronics/cmsis_device_h7`. The header is
1.77 MB; it was read on Monday 9 November 2026 by parsing the enum
programmatically rather than by reading it, because a table of 155 numbers must
not pass through a paraphrase. The parser refuses if any line in the enum body
that looks like an enumerator fails to parse, which is the check that matters: a
pattern matching most rows produces a table that looks complete.

`[vendor]` **The positions of the peripherals this volume actually uses are
corroborated against Zephyr's device tree**, `dts/arm/st/h7/stm32h7.dtsi`, which
is a different vendor reading the same silicon. `gen_vectors.py` refuses to write
a line of C if any of them disagrees.

| Peripheral | ST's `IRQn_Type` | Zephyr's node | Vector |
|---|---|---|---|
| USART3, the console | `USART3_IRQn = 39` | `usart3: serial@40004800`, `interrupts = <39 0>` | 55 |
| FDCAN1 line 0 | `FDCAN1_IT0_IRQn = 19` | `fdcan1: can@4000a000`, `interrupts = <19 0>, ...` | 35 |
| FDCAN1 line 1 | `FDCAN1_IT1_IRQn = 21` | `fdcan1: can@4000a000`, `..., <21 0>, ...` | 37 |
| FDCAN calibration | `FDCAN_CAL_IRQn = 63` | `fdcan1: can@4000a000`, `..., <63 0>` | 79 |

Zephyr's node for the bus is `can@4000a000`, which is also the register base
chapter 9 recorded in [`node-registers.md`](../ch09-can-fd-from-the-controller-out/doc/node-registers.md).
That is the third vendor source to agree on that address.

`[vendor]` **The alignment floor is ARM's.** `SCB_VTOR_TBLOFF_Pos` is 7 in CMSIS
`core_cm7.h`, so VTOR holds bits [31:7] of the table's base and cannot express a
base finer than 128 bytes.

## Three things about this table that fail silently

**A short table links and reports a sensible size.** The sixteen entry version
was correct for exactly as long as nothing enabled a device interrupt. The moment
something did, the core would have fetched a handler from past the end of the
table and branched to whatever word of flash followed it.

**Omitting the reserved positions displaces every later handler.** 134 of the 155
device positions carry a name and 21 do not, and the unnamed ones are scattered
through the range rather than gathered at the end: the first is 61. A table built
from the list of named interrupts is 21 entries short and puts the wrong handler
at every position above 61.

The console's USART3 is at position 39, which is BELOW that first gap, and that
is the worst available version of this defect: the one peripheral this chapter
brings up first is the one that would not reveal it. The bus is at 19 and 21,
also below the gap. The first thing that would have shown it is `FDCAN_CAL` at
63, four positions past the gap, which is also the least likely interrupt in this
volume to be enabled.

**The alignment depends on the length.** 171 entries is 684 bytes, so the base
needs 1024 byte alignment; the sixteen entry table needed 128. The script said
`ALIGN(512)`, which was generous for 64 bytes and too small for 684. It was not
wrong when written. A linker script cannot read a C header, so the number cannot
be generated into the script the way the `MEMORY` block is generated from the
memory map; `test_startup.py` reads `BOARD_ISR_ALIGN` from the generated header
and the script's `ALIGN` and refuses a mismatch.

`[unconfirmed]` The rule that the base must be aligned to a power of two at least
as large as the table is asserted from the ARMv7-M reference and NOT from a
source this bench can read. It is marked and then satisfied anyway: over
aligning costs flash padding and nothing else, and the alternative is a base that
is legal for the register and wrong for the core. Today the table also sits at
the boot address, `0x08000000`, which is aligned to far more than 1024, so the
directive is not what makes the current image correct. What it does is stop the
requirement being broken quietly if the table ever moves.

## Why the reserved positions hold a zero

Both the architecture's five reserved core slots and the part's twenty one
reserved device slots hold `0u`, which is what ST's own startup file does.

A reserved position is one nothing on this part is wired to, so it cannot fire
unless software pends it deliberately through the NVIC, and nothing here does. If
one ever did fire, a zero is the loud outcome rather than the quiet one: the core
reads it as the handler address and branches to 0 with the Thumb bit clear, which
faults. A default handler there would stop in a loop indistinguishable from every
other default handler stop.

What the reserved positions are not is omitted. They occupy their entries.

## Absence in this table is a statement, not a silence

Chapter 4 sets `BOARD_HAS_ETHERNET` to 0 and cites this table as the proof. That
is now a gated claim rather than an asserted one.

`[vendor]` Positions 61 and 62 are reserved on the STM32H7A3. On the STM32H743,
the better known sibling in the same family and the same vendor repository, the
same two positions are:

| Position | STM32H7A3 | STM32H743 |
|---|---|---|
| 61 | reserved | `ETH_IRQn`, Ethernet global Interrupt |
| 62 | reserved | `ETH_WKUP_IRQn`, Ethernet Wakeup through EXTI line Interrupt |

Read from `Include/stm32h743xx.h` on Monday 9 November 2026. Two headers from one
vendor, and the difference between them is the fact: this part has no Ethernet,
and the hole where the sibling's interrupt sits is where that shows.

`gen_vectors.py` refuses to write a line of C if either position ever acquires a
name, because at that point the chapter's claim and the table disagree and one of
them is wrong.

These are also the first two reserved positions, which is why they are the
example in the argument above about omitting the holes.

## How a chapter uses one

Every device handler is a **weak alias** to `Default_Handler_alias`, under the
vendor's own name, so a chapter defines one by defining it:

```c
void FDCAN1_IT0_IRQHandler(void)
{
    /* the strong definition wins, and nothing else changes */
}
```

The weakness is load bearing and `test_vectors.py` checks it: a strong definition
here would turn that override into a duplicate symbol error.

`vectors.h` also carries `BOARD_IRQ_<name>` for every named position, which is
what goes to the NVIC to enable one. A wrong constant there enables the wrong
interrupt, which is exactly as quiet as a wrong vector, so the corroborated four
are checked against Zephyr there too.

Nothing in this volume enables a device interrupt yet.

## What this does not establish

`[unconfirmed]` That any of these handlers is ever reached. No image in this
volume has run, no interrupt has been enabled, and a vector table is the one part
of a startup whose correctness is invisible until something fires. What has been
established is that the positions are the vendor's, that two vendors agree on the
four that matter, that the table is as long as the highest position plus one, and
that it links at the boot address with the alignment its length requires.
